# 성능 측정 · v0.11.1

2026-10-29, 같은 개발 환경의 Chromium에서 12번 샘플(원본 10,000행 / 새 파일 10,010행)을 측정했습니다. 아래는 단일 실행의 관측값이며 서버 부하·캐시·네트워크에 따라 달라집니다. 캐시가 섞이는 샘플 생성/최초 로딩 시간은 전후 비교에서 제외했습니다.

| 구간 | v0.11.0 | v0.11.1 |
| --- | ---: | ---: |
| 기준열 선택 → 표 표시 | 2.05초 | 1.10초 |
| 저장 클릭 → 다운로드 | 5.16초 | 2.84초 |
| 개별 체크의 동기 JS 처리 | 12.8ms | 2.0ms |
| 표 데이터의 컴포넌트 인자 크기 | 4,958,119바이트 | 606,228바이트 |

표 전체를 갱신하는 시간은 이 측정에서 약 24~30ms로 뚜렷한 개선이 없었습니다. 전체 재렌더링이 빨라졌다고 주장하지 않습니다. 체크는 변경된 행의 결과만 계산하고 화면의 해당 행을 갱신하며, 저장 시 이미 열린 표 데이터는 재전송하지 않습니다. 모든 행은 계속 검색·스크롤할 수 있습니다.

엔진 측정(`python benchmarks/sample12.py`)에서는 시트 목록 두 번 읽기가 약 1.2초에서 0.001초로 줄었습니다. 비교 계산 자체는 약 0.06~0.09초입니다. 남는 주된 비용은 실제 XLSX 읽기·쓰기와 처음 표를 전달하는 과정입니다.

## 실제 수십 MB 파일

압축 안 되는 무작위 텍스트를 셀에 넣은 원본 **24,732,671바이트**, 새 파일 **6,226,301바이트**를 만들었습니다. 원본은 4,500행 × 5열이고, 네 텍스트 열은 셀마다 1,800자입니다. ZIP에 의미 없는 파일을 덧붙여 용량만 늘린 데이터가 아닙니다.

개발 환경에서 실제 업로드·비교·45건 중 1건 취소·결과 다운로드를 검증했습니다. 관측값은 업로드/읽기 약 2~3초, 비교/최초 표시 약 13~15초, 다운로드 약 9.4초였습니다. 저장된 파일을 다시 열어 **4,500행, 수정 44건, 취소한 값과 원본 전용 세 열 유지**를 확인했습니다. 파일 용량만으로 모든 파일에 같은 속도를 보장하지 않습니다. 이런 파일의 최초 표 전달에는 아직 개선 여지가 있습니다.

## 회귀 검증

- 자동 테스트 44개 통과.
- 실제 브라우저에서 색상, 변경 이동, 3개 표 확대, 로컬 체크, 결과/설정 다운로드, 패널 접기/펼치기 확인.
- 저장 후 표 데이터 재전송 없음 확인. 컴포넌트 재로드 시 자동 재요청으로 복구되는지 확인.
- 엑셀 끝 행/끝 열까지 서식만 있는 파일에서 빈 셀 전체를 만들어 순회하지 않고 실제 데이터만 읽는 회귀 테스트.
- 저장 메타데이터를 얻을 때 파일을 다시 열지 않고, 출력 파일과 같은 행 순서/값/이력이 나오는지 확인.

## 공개 앱 확인

동일한 공개 URL에서 v0.11.0과 v0.11.1을 각각 실행해 확인했습니다. 기준열 선택부터 표 표시까지 **3.23초 → 1.97초**, 저장 클릭부터 다운로드까지 **13.00초 → 7.62초**, 동기 체크 처리 **12.6ms → 5.7ms**였습니다. 각 1회 측정이며 캐시 상태가 달랐던 최초 샘플 로딩 시간은 비교하지 않았습니다. 전체 렌더링 시간은 개선되지 않았고 변동이 있어 성능 보장값으로 사용하지 않습니다.

공개 앱의 결과 파일도 다시 열어 10,010행과 수정 1,664셀·추가 15·삭제 5를 확인했습니다. 수정 1건을 취소한 상태로 저장한 결과입니다.

최적화: source style ID를 목적 워크북의 스타일로 처음 한 번 등록하고 목적 스타일만 복제합니다(출처 스타일 ID를 워크북 사이에 직접 복사하지 않음). 메모·하이퍼링크는 셀별로 복사합니다. 행 추가의 max_row/max_column 반복 순회를 제거했고, 반영 결과의 Table/레이아웃을 세션별 제한 캐시에 넣어 다음 단계 재파싱을 피합니다. 동일한 선택·복사·정렬의 결과는 재생성하지 않습니다. 같은 양식 다음 파일의 너비 맞춤은 원본 전체를 다시 재지 않고 새 비교값을 기준으로 확장합니다. 백그라운드 prefetch는 이번에 도입하지 않았습니다.

재현: `python benchmarks/collection.py`(프로젝트 의존성이 설치된 Python), 또는 `python tests/browser/release_v24.py --only collection_performance.py --url http://localhost:8524 --baseline-url http://localhost:8527`. 기준 버전은 별도 임시 체크아웃에서 8527 포트로 실행합니다. 초기 업로드/샘플 생성 시간과 마지막 완료 다운로드는 전환 측정에서 제외합니다. 브라우저 측정기의 첫 시도는 샘플 로딩 완료 대기가 부족하여 실패했으며, 명시적인 샘플 실행·준비 상태 확인 후 재측정했습니다.

## Native0.3 스크롤 진단 — 2026-11-02, 구현 전 기준

사용자: 0.3 EXE 스크롤이 여전히 부드럽지 않으니 성능 향상 가능 여부 문의. 새 단독 `해` 전이므로 앱/테스트 코드는 수정하지 않고 임시 진단만 수행했다.

조건: Linux Qt6.8.3/offscreen, Noto Sans KR Desktop13px, 창1550×930, 실제 샘플5/12, 스크롤바를27px씩100회 이동하고 매번 processEvents. 앞10회 제외한90회 처리 시간을 측정했다. 애니메이션 대기 시간을 측정한 것이 아니며 Windows 실제 주사율/FPS·실제 휠 체감과 다르다. 진단 스크립트는 `/tmp/profile_native_scroll.py`(임시파일, 환경 재시작 시 소실 가능). 원본 코드 변경 없음.

| 샘플 | 보기 | 행 수 | 변경 수 | 처리 중앙값 | P95 |
|---|---|---:|---:|---:|---:|
|5|나눠보기|515|60|47.80ms|57.04ms|
|5|합쳐보기|515|60|24.99ms|30.27ms|
|12|나눠보기|10015|1685|53.59ms|64.51ms|

별도 cProfile50회(프로파일러 오버헤드 포함, 위 시간과 직접 합산/비교 금지): 샘플12 나눠보기4.814초 중 MergeDelegate.paint3.616초, 그 안 initStyleOption2.066초, drawControl1.034초. GridModel.data124,488회, change85,176회/1.103초, 이 과정에서 같은 key의 json.dumps85,176회/0.409초. 레일 paint150회/0.360초. 합쳐보기는 paint2.150/총2.671초로 같은 경향. 주요 비용은 셀 그리기·스타일 조회·상태 재조회이며 원본 비교 엔진 재실행이 아니다.

다음 구현 방향(미구현):
1. 행 인덱스로 변경 상태를 직접 조회해 셀마다 JSON 인코딩/역조회하지 않기. data에서 지원하지 않는 Qt role은 즉시 반환.
2. 선택/값/테마/복사 방식·배율 등 실제 상태 변경 시만 무효화되는 표시 캐시. 일반 텍스트 셀은 필요한 배경/텍스트/테두리만 그리는 빠른 경로를 검토하되 변경색·선택선·빗금·체크·수식/값 표시/줄바꿈 보존.
3. 인디케이터는 구간/이미지를 캐시해 스크롤 중 핸들만 갱신하고 반복 marker fillRect 축소.3표 스크롤 동기화의 중복 갱신도 계측.
4. 반복 휠 입력마다100ms 애니메이션을 stop/start하는 방식은 프레임 비용 개선 후 재검토. 같은 방향 입력은 목표를 갱신하는 연속 보간, 반대 방향/드래그는 즉시 반응. 과한 관성 금지, Shift/Ctrl 구분 유지.
5. 동일 조건에서 전후 중앙값/P95와 실제 100ms 휠 프레임 간격을 비교하고 선택·표시 회귀 및 최종 Windows EXE 검증. 개선율/FPS 목표를 측정 전에 보장하지 않는다.

## Native0.4 스크롤 개선 — 2026-11-03

앞 절 Native0.3과 동일 Linux/offscreen/창/샘플/27px×100회 조건, 첫10회 제외. 아래 샘플 번호는 **기존 내부 fixture 번호**이며 새 네이티브 메뉴의4/5번에 해당한다. UI 변경 후 별도 프로파일링과 분리하여 측정했다.
